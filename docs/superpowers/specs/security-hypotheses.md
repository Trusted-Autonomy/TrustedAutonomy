# TA Security Hypotheses

A running ledger of adversarial hypotheses about TA's security boundaries. Each one is a concrete claim about what an attacker, a prompt injection, or an
errant agent cannot do, backed by a real test against the live system (never
a mock of the thing being tested). Started 2026-10-05 alongside the
chat-mode secure launch primitive; extend this whenever a new security
boundary is built, or a real incident/finding surfaces (same spirit as the
2026-08-24 TA red-team review).

Status values: **blocked** (a real test proves the attack fails today),
**open** (identified, not yet covered by a test), **regressed** (was blocked; a later change broke it, and this is treated as a P0 bug).

## Not yet covered (open, tracked for future work)

- Whether a chat-mode agent process can bypass manifest enforcement entirely by using a native tool (Bash, native file read/write) instead of TA's mediated MCP tools, rather than any gap in the manifest or `PolicyEngine` itself. This is a tool-surface-restriction question, addressed by design in `docs/superpowers/specs/2026-10-05-chat-mode-secure-launch-design.md`'s Phase 1 item 3, but not yet covered by a test here because the actual wiring (which repo/process grants the chat agent its tools) is in `ta-virtual-team`, out of scope for this plan.
- OS-level sandbox backstop (Phase 2 in the same design doc). No test here until that phase is designed.
- **H5 (resolved 2026-10-06, `fix/cos-security-hardening`):** fixed at three layers. `check_policy()` now rejects any non-workspace-relative path (absolute POSIX/Windows/UNC forms, `~`, `..` components) before building the `fs://workspace/` URI and normalizes `./` and `//`; `ta_workspace::path_safety::resolve_within_root` (used by `FsConnector::read_source` and `StagingWorkspace` read/write) rejects the same lexical forms and canonicalizes the deepest existing ancestor to reject symlink escapes; `SECRET_PATH_PATTERNS` now also covers `.aws/credentials`, `.aws/config`, `.ssh/**`, `.config/gcloud/**`, `.netrc`/`_netrc`, `.docker/config.json`, `.kube/config`, `.git-credentials`, `.gnupg/**`, `Library/Keychains/**`, `*.keychain`, `*.keychain-db`, matched with both `/` and `\` separators. Known, deliberate tradeoff: in a smart-mode staging overlay, excluded directories are symlinks back to the source project, so they are no longer readable through `ta_fs_read` (the symlink resolves outside the staging root); agents read those through their native tools, and a fail-closed default is preferred to a heuristic exemption.
- **H7 depends on the persona declaring itself read-only.** TA core now enforces the read-only surface for any persona with `read_only = true` in `[capabilities]`, but the Chief-of-Staff persona file lives in `ta-virtual-team` (`chief-of-staff.toml`), which must set `read_only = true` (and either omit `allowed_tools` or list only read-only TA MCP tools) for H7 to apply to the real CoS. Until it does, a CoS launched with an empty `allowed_tools` still falls back to the broad default allow-list. The whiteboard tools CoS may legitimately need for dispatch (`ta_whiteboard_handoff_send`, `ta_whiteboard_presence_register`) are classified mutating and are therefore excluded; CoS dispatch is expected to go through the poller's hardened `ta run`, per the CoS read-only chat-mode design.
- **H8, routing constrained by task type (open).** TA core has no task-type to allowed-persona mapping to test. `ta_brain::route()` (`crates/ta-brain/src/route.rs::resolve_persona`) lets an explicit `--persona` or a trigger's `persona_hint` win over the `[workload_types.<type>].persona` binding with no allowed-set check, and `TeamConfig::find_by_tag`/`handles_tags` (`crates/ta-session/src/team.rs`) is documented as a routing hint consulted only by a virtual team's own orchestrator, never by TA core. The mapping CoS actually uses lives in `ta-virtual-team` (its CoS dispatch path) and, once reconciled per design-doc dispatch item 5, Wayfinder's `team_role_verb`/`handles_verbs`. The covering test belongs in `ta-virtual-team`'s CoS dispatch code: given a classified task type and a prompt-injected routing output naming a persona outside that type's allowed set (for example a wiki-edit task routed to a developer-class persona, or to `chief-of-staff` itself), the dispatcher must refuse or clamp to the allowed set before any `ta run` is issued, asserted on the real dispatch function, not a mock. If the allowed-set check is later moved into TA core (for example as an allowed-persona constraint in `ta_brain::route` keyed by workload type, which would also close the `persona_hint` gap above), the test should move with it.
- **H9 scope notes.** Enforcement is keyed on `GoalRun::origin`, so it applies once the dispatcher stamps it: `ta-virtual-team` must launch CoS-dispatched goals with `ta run --origin cos` (or `TA_GOAL_ORIGIN=cos`). `ta run --origin` exports `TA_GOAL_ORIGIN`, so nested `ta` invocations from that goal inherit it. The advisor clamp (`AdvisorSecurity::clamped_for_origin`, used by `WorkflowContext::effective_security`) covers the `ActionRouter` primitives; `WorkflowContext` has no production constructor today, and the Studio advisor endpoint (`crates/ta-daemon/src/api/advisor.rs`) and team-session per-role `--security` are not goal-bound, so they carry no origin to clamp on. Any future production path that lets an advisor act on behalf of a goal must build its `WorkflowContext` with `.with_origin(goal.origin)`. `check_advisor_auto_approve` (`crates/ta-session/src/advisor_agent.rs`) has zero production callers (see `apps/ta-cli/tests/constitution_16_3_call_site.rs`) and was left unchanged.
- **H5, absolute-path workspace escape (pre-existing, found during final whole-branch review of chat-mode secure launch Phase 1, 2026-10-05):** `check_policy()` in `crates/ta-mcp-gateway/src/server.rs` builds the target URI as `format!("fs://workspace/{}", path)`. When `path` is an absolute path (e.g. `/Users/me/.aws/credentials`), the result is `fs://workspace//Users/me/.aws/credentials`, which the glob pattern `fs://workspace/**` still matches, so the grant check passes. Separately, `crates/ta-connectors/fs/src/connector.rs`'s `read_source()`/`write_patch()` join the (attacker-controlled) relative path onto the source/staging base directory using `PathBuf::join()`, which discards the base entirely when the joined path is absolute, reaching arbitrary absolute paths on disk, not just workspace files. This means the design's "read anywhere in the workspace" grant for chat mode can, in practice, read anywhere on disk the process can see. Compounding this, the secrets backstop's `SECRET_PATH_PATTERNS` (`crates/ta-policy/src/engine.rs`) only covers workspace-relative secret filenames (`.env`, `credentials.json`, `*.pem`, `*.key`, `id_rsa*`) and does not cover common absolute-path secret locations such as `~/.aws/credentials` or `~/.ssh/id_ed25519`. Not fixed here: per the review's recommendation, this is recorded for a future session rather than fixed in this branch (out of scope, pre-existing, not introduced by this work). Starting points for whoever picks this up: the URI construction in `check_policy()` (`crates/ta-mcp-gateway/src/server.rs`) and the path joining in `read_source`/`write_patch` (`crates/ta-connectors/fs/src/connector.rs`).

- **CoS outbound channel (added on PR #640):** the chat profile now holds `ta_whiteboard_outcome_send` (the Chief-of-Staff's only outbound channel) and `ta_ask_human`. `ta_context` (store/forget write cross-agent memory) and `ta_human_verify` (spawns headless agents) are deliberately excluded and covered by `chat_profile_contains_no_mutating_tools`. Residual trust: what an outcome can cause is enforced by the poller in `ta-virtual-team` (bound to in-flight candidates, capped, tag-validated, `--origin cos`, no auto-approve), not by TA core; a covering test belongs in that repo (open).
